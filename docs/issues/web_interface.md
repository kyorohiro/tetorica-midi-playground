# Native／Browserのインターフェース方針

2026-09-22の設計相談の記録。ブラウザー版や共通バックエンドは未実装であり、以下は今後の機能追加時に意識する方針。

AIは作業前に [save_point.md](save_point.md) を参照すること。

## 優先すること

当面はネイティブ版の完成度を優先する。ブラウザー対応を同時に進めると、MIDI接続・音声出力・発音タイミング・停止処理の実装と検証が増える。今回の方針だけを理由にブラウザー版を実装しない。

## 現在の流れ

1. ユーザーの演奏コードが `midi.output(...).play(...)` などを呼ぶ。
2. Worker（`ui/runner.js`）がループ・拍・演奏要求を扱う。
3. `ui/app.js` がWorkerからの要求を受け、Tauriの `invoke()` でネイティブ側を呼ぶ。
4. Rust側がMIDIメッセージを出力先へ送る。内蔵IDは自身の音源キューへ直接接続する。外部アプリからの入力には仮想MIDIポートを引き続き使用する。
5. 内蔵YM2612ではネイティブのymfmが波形を生成し、ミキサーとcpal経由で音声を出力する。

内蔵音源と外部音源に共通のMIDIインターフェースがあることを活かす。

## どこで切るか

「Workerから先の環境差を吸収する」と考える。ただし、Worker内にNative／Browserの分岐を集めるのではなく、現在の `ui/app.js` が演奏要求を受けて `invoke()` する接続部分を境界とするのが第一候補。

```text
ユーザーの演奏コード
        ↓
共通のWorker：ループ・拍・演奏要求
        ↓
共通の要求／応答の契約
        ├─ Native用の接続処理 → Tauri → Rust → MIDI・音源
        └─ Browser用の接続処理 → ブラウザー音源など（将来）
```

Workerは実行環境を知らず、発音・停止などを要求する。ユーザーの演奏APIも可能な限り共通に保つ。

## 境界で扱う操作と意味

具体的なインターフェース名・メソッド構成は未決定。次の操作と意味を揃える。

- 音源の有効化。
- MIDI出力先の解決・接続と、その識別子。
- 音程・チャンネル・音量・長さを含む発音要求。
- 特定ループの発音解除と、演奏全体の停止。
- 要求に対する完了通知・エラー通知。
- Runの世代、ループの所有者を使った古い要求の拒否と停止管理。

音の長さや停止対象まで渡し、実際の発音・消音管理は環境別の実装に任せる。現在ネイティブ側が担うNote Offの管理を、単にJavaScriptのタイマーへ移さない。要求受付と演奏完了の意味を混同しないよう、応答と待機の契約を明確にする。

## 機能追加時に確認すること

- ループや演奏コードの意味に関わる処理か、機器・実行環境に依存する処理か。
- 共通Workerや演奏APIにTauri、DOM、ブラウザー音声APIへの直接依存を増やしていないか。
- Run／Apply／Stop、停止後の遅延要求、エラー時の消音という既存の挙動を保てるか。
- 音色編集・Mixer・MIDI Clock・ポート列挙など、演奏以外の機能にも別途境界が必要ではないか。

将来のブラウザー版では、元のYM2612 PlaygroundのWASM音源をMIDI出力のインターフェースで包む案がある。ただし、タイミング・音色設定・停止処理を含めた対応が必要で、接続先の差し替えだけで完成するとは想定しない。

既存コード全体の分割は今すぐ行う必要はない。依頼された機能の範囲で境界を保ち、具体的な分割が必要になった時点でこのメモを設計に反映する。

## 内蔵出力の識別（2026-09-24 修正）

`tetorica-ym2612` / `tetorica-sega-psg` と MIDI 設定の internal 出力は、このアプリ自身のラックへ接続する。同名の仮想ポートが複数あっても名前検索をしない。MIDI メッセージ・SysEx の処理は外部からの入力と共通。ラックを無効化した古い接続はエラーにし、別のラックへ転送しない。外部ポートの名前が重複する場合は、従来どおりポート ID で指定する。
